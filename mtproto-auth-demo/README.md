# auth_key lab — живая демонстрация рукопожатия MTProto

Интерактивный сайт, который показывает, как клиент Telegram и сервер создают ключ авторизации
(`auth_key`) по протоколу из документации:
[samples-auth_key](https://core.telegram.org/mtproto/samples-auth_key) и
[Creating an Authorization Key](https://core.telegram.org/mtproto/auth_key).

Ничего не имитируется «на картинках»: TL-сериализация, RSA_PAD, AES-256-IGE, факторизация `pq`,
Диффи — Хеллман на 2048 битах, SHA1/SHA256 и все проверки безопасности выполняются по-настоящему,
прямо в браузере. Обе стороны рукопожатия обмениваются сырыми байтами MTProto-сообщений, которые
сайт показывает в виде hex-дампа с подсветкой полей.

## Запуск

Сборка не нужна — это статические файлы и нативные ES-модули.

```bash
# из корня репозитория
python3 -m http.server 3000 --bind 0.0.0.0 --directory mtproto-auth-demo
# открыть http://localhost:3000
```

Подойдёт любой статический сервер (`npx serve`, `php -S`, nginx). Открывать `index.html`
как `file://` нельзя: браузер не даст модулям загрузиться, а `crypto.subtle` требует
защищённого контекста (`https://` или `localhost`).

## Что происходит на экране

| Шаг | Что делает | Ключевые сущности |
| --- | --- | --- |
| 0 | сервер генерирует пару RSA-2048 | `n`, `e`, отпечаток = 64 младших бита SHA1 |
| 1 | client → server `req_pq_multi` | `nonce` |
| 2 | server → client `resPQ` | `server_nonce`, `pq`, отпечатки ключей |
| 3 | клиент раскладывает `pq` (proof of work) | ро-алгоритм Полларда — Брента |
| 4 | client → server `req_DH_params` | `new_nonce`, `RSA_PAD` (8 шагов набивки) |
| 5 | server → client `server_DH_params_ok` | `g`, `dh_prime`, `g_a`, AES-256-IGE |
| 6 | клиент расшифровывает и проверяет параметры | безопасное простое, Миллер — Рабин, границы `g_a` |
| 7 | client → server `set_client_DH_params` | секрет `b`, `g_b` |
| 8 | клиент считает `auth_key` | `g_a^b mod dh_prime`, `auth_key_id` |
| 9 | server → client `dh_gen_ok` | `g_b^a mod dh_prime`, `new_nonce_hash1` |
| 10 | сверка результатов | `server_salt`, совпадение ключей |

## Структура

```
index.html            разметка страницы
assets/styles.css      оформление
src/bytes.js           hex, конкатенация, XOR, случайные байты
src/hash.js            SHA1/SHA256 поверх WebCrypto
src/aes.js             AES-256 (чистый JS) + режим IGE
src/bigint.js          BigInt-арифметика, факторизация, Миллер — Рабин
src/tl.js              (де)сериализация TL + карта полей для hex-дампа
src/rsa.js             генерация ключа, отпечаток, RSA_PAD / обратное преобразование
src/protocol.js        номера конструкторов TL-схемы, dh_prime, g
src/server.js          модель серверной стороны рукопожатия
src/handshake.js       клиентская сторона + сценарий шагов
src/app.js             интерфейс: карточки шагов, hex-дампы, панель состояния
test/                  проверки под Node (без браузера)
```

## Тесты

```bash
cd mtproto-auth-demo
node test/aes.test.mjs        # AES-256 на векторе FIPS-197 + AES-IGE на векторе Telegram
node test/handshake.test.mjs  # сквозное рукопожатие: ключи сторон должны совпасть
node test/ui.smoke.mjs        # прогон сценария интерфейса с заглушкой DOM
```

`test/aes.test.mjs` расшифровывает `encrypted_answer` из официального примера Telegram
настоящим `tmp_aes_key`/`tmp_aes_iv` и убеждается, что получилась структура
`server_DH_inner_data` с правильным SHA1 и известным `dh_prime`. То есть реализация IGE
совместима с боевой.

## Ограничения модели

* Браузер не умеет открывать TCP-соединение с дата-центром Telegram, поэтому вторая сторона —
  локальная модель сервера (`src/server.js`). Она честно выполняет свою половину протокола,
  но живёт в той же вкладке.
* Сервер генерирует собственную пару RSA: приватные ключи настоящих серверов Telegram никому не
  известны, а без них расшифровку `req_DH_params` показать невозможно.
* Значение `dh_prime` взято настоящее — то, которое приведено в документации.
* Транспортные заголовки (abridged/intermediate) опущены, как и в примере из документации.
* Это учебный код: генератор случайных чисел браузерный, защиты от атак по времени нет —
  в продакшене так делать не нужно.
