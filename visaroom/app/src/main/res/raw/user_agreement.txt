4. DESCRIPTION OF THE SERVICE

4.2. Direct chats are cloud chats. Temporary memory, temporary recording files, explicit downloads, locally stored settings, session material, encrypted local E2EE private keys, profile cache and notification-deduplication markers are not a local history database.

4.3. The one-to-one protocol used by the app is called VRProto in the technical implementation. It is a custom client/Firestore protocol. It is not Telegram’s MTProto, and visaroom is not affiliated with Telegram.

5. IMPORTANT PRIVACY AND ENCRYPTION LIMITS

5.1. Protocol 2 direct-message text and reply snapshots, private file and voice-message metadata and chunks, and encrypted per-chat wallpaper images are end-to-end encrypted on a participant device before upload. Firestore stores ciphertext, public keys, signatures/wrapped message keys, participant and message identifiers, timestamps, ciphertext sizes, download counters and a generic “Encrypted message” preview. Private decryption keys are designed to remain only on participant devices; an optional cloud key backup is stored only as ciphertext under a separate recovery password chosen by the account holder. The operator and a person with privileged Firebase project access are therefore not intended to possess the keys needed to read protocol 2 direct-message content from Firestore. Chat metadata can still reveal who communicated, when, message sizes and whether an attachment exists. Public/profile information and official announcements are not private direct messages and are not protected as E2EE direct-message content. Messages created before protocol 2 may remain legacy plaintext in Firestore until their sender migrates or deletes them; the updated app labels legacy messages and best-effort migrates a sender’s own legacy text messages when the chat is opened with both participants’ keys available.

5.2. End-to-end encryption protects content from the cloud database, not from a compromised endpoint, a person using your unlocked device, malware, a weak or reused key-backup password, or the other participant. Keep devices and accounts secure, use a strong unique recovery password if you create a key backup, compare safety codes when identity assurance matters, and do not use visaroom for information that would cause serious harm if an endpoint or recipient disclosed it.

5.3. The app uses authenticated E2EE envelopes, identity-key fingerprints/safety codes and key-change warnings, transport security, Android Keystore protection for saved refresh tokens and local E2EE private keys, application hardening, password-derived two-step verifiers and Firestore Security Rules. These measures reduce risk but do not make the service perfectly secure. If all devices and the key-backup password are lost, previous E2EE history may be permanently unreadable; resetting keys creates a new identity and other participants will see a key change. No internet service can guarantee absolute security.

5.4. A recipient can copy, photograph, record, download, quote or otherwise preserve content that you send to them. Deleting a message from visaroom does not delete copies outside visaroom and does not erase a recipient’s memory or independent records.

5.5. Profile fields marked or configured as visible may be viewed by other signed-in users according to the current privacy settings and security rules. Your email address is not intended to be public in ordinary profiles or username search, but you should not use a public username, biography or image that reveals information you do not want associated with the account.

5.6. For protocol 2 messages, cloud indexes and notifications are designed to use a generic encrypted-message preview rather than decrypted text. Legacy messages and device-level features may still expose a sender name or preview depending on system and channel settings. visaroom marks its notifications as private and supplies a generic public version, but device manufacturers, launchers, connected watches, cars and accessibility tools may handle notifications differently. You are responsible for your device notification settings.

8.3. To conserve cloud storage, each of the two participants in a direct chat has one completed-download slot for an ordinary file attachment. A counter such as 0/2, 1/2 or 2/2 may be shown. Only a fully completed download is intended to consume that participant’s slot. When both participants have completed a download and the counter is exhausted, the app may automatically delete the cloud chunks and file metadata while leaving the historical message envelope visible.

8.4. If you need to keep a file, save and back it up outside visaroom before the cloud copy is deleted. Once both download slots are used or the sender deletes the file message, visaroom may be unable to restore the cloud bytes.

8.6. Recording uses the microphone permission only when you start recording. Playback is designed to use memory rather than a permanent local chat download, but operating-system caches and crash remnants cannot be absolutely ruled out.

8.7. A voice message remains replayable while its cloud chunks remain available and the message has not been deleted, unless a later version changes this behaviour with notice in an updated Agreement or release information.
