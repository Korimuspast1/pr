# Пассивный аудит безопасности — `kem-rp.com`

**Дата:** 27 ноября 2026
**Объект:** `kem-rp.com` + `api.` `fs.` `ws.` `adm.` `status.` `global.` `media.` поддомены
**Тип работ:** пассивный анализ поверхности (black-box, без учётных данных)
**Основание:** заявленное разрешение владельца

---

## 1. Границы работ

Проверялось **только то, что сайт отдаёт любому анонимному посетителю**: DNS-записи,
TLS-параметры, HTTP-заголовки, публичные файлы (`robots.txt`), клиентский JavaScript
и публичные API-эндпоинты без авторизации.

**Сознательно не выполнялось** (даже при наличии разрешения):

| Не делалось | Почему |
|---|---|
| Перебор путей/директорий, брутфорс | Создаёт нагрузку на прод, ломает доступ живым игрокам |
| Инъекции (SQLi/XSS-payload'ы), обход авторизации | Активная эксплуатация на боевом сервисе с реальной аудиторией |
| Нагрузочные тесты | Прямой риск простоя |
| Любая работа под чужой учётной записью | Не требуется и недопустимо |

Из-за этого часть находок имеет статус **«требует проверки с авторизацией»** — я честно
помечаю их отдельно и даю чек-лист в разделе 5. Разрешение владельца не отменяет того,
что аудит не должен ронять работающий сервис.

## 3. Находки

### 🔴 H-1. Инъекция CSS / `url()` через пользовательское оформление, рендерится у других

**Где:** `core/user.service.js` → `applyNickStyle()`, `applyTopAvatarFrame()`;
`core/index.page.js` → `renderTopPlayers()`.

Данные профиля из API пишутся в стили **без какой-либо валидации**:

```js
wrap.style.cssText = frame.css_style;              // произвольный cssText целиком
el.style.setProperty('--grad-from', user.nick_gradient.from);  // без проверки формата
el.style.color = user.nick_color || '';            // без проверки формата
```

Это не только «свой» экран: `renderTopAvatar()` и топ игроков рисуют **чужую** косметику
на главной странице и в шапке у всех посетителей.

CSS-инъекция в современных браузерах сама по себе не даёт выполнения JS, но позволяет:
подменять/скрывать элементы интерфейса, накладывать прозрачные оверлеи поверх кнопок
(UI-redressing, кража клика), подгружать внешние `url()` — то есть уводить факт
посещения и портить интерфейс всем сразу. При наличии в `css_style` конструкции
`url(javascript:...)` в старых движках возможен и худший сценарий.

**Починка:**
- на сервере **и** на клиенте: `nick_color` / `gradient.from` / `gradient.to` — строго
  `^#[0-9a-fA-F]{3,8}$`;
- `frame.css_style` — либо убрать совсем, либо заменить на whitelist из 3–5 свойств
  (`border`, `box-shadow`, `border-radius`) с валидацией каждого значения;
- `frame.image_url` — проверять схему (`https:` только) перед подстановкой в `src`.

### 🔴 H-2. Экранирование — самописный `escapeHtml`, скопированный в 4+ модулях

Одна и та же функция продублирована в `index.page.js`, `user.service.js`,
`profile.settings.page.js`, `promo.service.js` и др. Классическая предпосылка
stored-XSS: достаточно одного места, где забыли вызвать (или вызвали «не тот» вариант),
и пользовательский `username` / `bio` / `status` / комментарий форума исполняется у других.

Отдельно: `escapeHtml` корректно закрывает `& < > " '`, но **не валидирует схемы URL** —
а значения из API подставляются в `src`/`href` (`avatar`, `banner`, `image_url`,
`thumbnail_url`). `javascript:`/`data:` в таком поле = XSS мимо экранирования.

**Починка:** один модуль `shared/escape.js` с `escapeHtml()` + `safeUrl()` (разрешены
только `https:` и относительные пути), импортировать везде; для вставки в атрибуты —
отдельный `escapeAttr`. Серверная валидация URL обязательна (клиентскую можно обойти).

### 🟠 M-1. На главном HTML-хосте нет CSP

API отдаёт `Content-Security-Policy`, а **сам сайт — нет**, хотя именно там живёт весь
пользовательский контент. При этом CSP у API довольно мягкий:
`script-src 'self' 'unsafe-inline' 'unsafe-eval'` — то есть даже если перенести его
на сайт как есть, защита от XSS будет близка к нулю.

**Починка:** CSP с nonce/hash на `kem-rp.com`, без `unsafe-inline`/`unsafe-eval`;
как первый шаг — `Content-Security-Policy-Report-Only`, чтобы собрать нарушения.

### 🟠 M-2. Нет HSTS ни на одном хосте

`Strict-Transport-Security` не обнаружен ни на `kem-rp.com`, ни на `api.`, ни на `adm.`.
Редирект `http → https` есть (301), но его можно срезать на первом визите (sslstrip).

**Починка:** `add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;`
Wildcard-сертификат покрывает все поддомены, так что `includeSubDomains` безопасен.

### 🟠 M-3. Страницы ошибок отвечают HTTP 200

```
/errors/404            code=200   <title>Страница не найдена</title>
/errors/403            code=200
/nope-page-zzz         code=302 → /errors/404 (тоже 200)
```

Следствия: мониторинг не видит падений, поисковики индексируют «не найдено», кэши/CDN
считают ответ успешным. **Починка:** отдавать реальные 404/403.

### 🟠 M-4. На корне `api.` и `fs.` открыта заглушка хостинга reg.ru

```
GET https://api.kem-rp.com/  →  200, 769 117 байт, text/html
GET https://fs.kem-rp.com/   →  200, 769 117 байт, тот же etag "bbc5d-63bce3ee9aa4f"
внутри: <html lang="ru" data-panel-url="https://vip254.hosting.reg.ru/manager">
```

То есть запросы, не попавшие в конфиг сайта, обслуживает **дефолтный vhost хостинга**.
Раскрывается имя аккаунта (`vip254`) и панель управления; посетитель, набравший
`api.kem-rp.com` без пути, видит страницу reg.ru вместо API — это и утечка, и сбивающая
с толку выдача. **Починка:** явный `location = / { return 404; }` (или 403) для `api.`
и `fs.`; для `fs.` — отдельный бакет-стиль ответ.

### 🟠 M-5. Почта: DMARC `p=none`, DKIM не найден, CAA нет

```
_dmarc   v=DMARC1; p=none; aspf=r; sp=none
TXT      v=spf1 ip4:31.31.196.228 a mx include:_spf.hosting.reg.ru ~all
CAA      (пусто)
DKIM     default._domainkey / mail / google / selector1 → NXDOMAIN
```

`p=none` — это режим наблюдения, он **ничего не блокирует**. При аудитории ~58 тыс.
участников и привязке аккаунтов Roblox фишинг с подделкой `@kem-rp.com` (письмо
«сброс пароля» от настоящего домена) — реалистичная атака. SPF `~all` (softfail) тоже
не отбраковывает.

**Починка по шагам:** включить DKIM на почтовом хосте → собрать отчёты `rua=` пару недель →
`p=quarantine` → `p=reject`. SPF: `~all` → `-all`, когда список отправителей стабилен.
CAA: `kem-rp.com. CAA 0 issue "letsencrypt.org"`.

### 🟠 M-6. Админка `adm.kem-rp.com` без единого защитного заголовка

```
HTTP/2 200
server: nginx
content-type: text/html
content-length: 1230
```
Ни `X-Frame-Options`, ни CSP, ни `nosniff`, ни HSTS. Админпанель без `frame-ancestors` /
`X-Frame-Options` = кликджекинг: панель можно встроить в iframe на чужой странице.
**Починка:** `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'` + `nosniff` + HSTS.

### 🟡 L-1. `TRACE` в списке разрешённых методов

```
allow: OPTIONS,HEAD,GET,POST,TRACE
```
`TRACE` нужен только для Cross-Site Tracing (устаревший вектор вместе с `XST`), никакой
прикладной задачи не решает. **Починка:** в nginx `if ($request_method = TRACE) { return 405; }`.

### 🟡 L-2. `X-XSS-Protection: 1; mode=block`

Заголовок устарел и в части браузеров legacy-фильтр сам создавал уязвимости.
**Починка:** `X-XSS-Protection: 0` либо убрать, положившись на CSP.

### 🟡 L-3. Wildcard DNS `*.kem-rp.com`

`nope-does-not-exist-zzz.kem-rp.com` → `31.31.196.228`. Любой поддомен существует, поэтому
опечатки в адресе ведут на прод, а инвентаризация поддоменов снаружи невозможна в принципе.
Не уязвимость, но стоит осознанно подтвердить, что так и задумано.

### 🟡 L-4. На `api.` выключен TLS 1.2

```
tls1_0 no   tls1_1 no   tls1_2 no   tls1_3 SUPPORTED
```
Современно и безопасно, но отсекает старые Android-устройства и часть встроенных
WebView — а у Roblox-аудитории таких много. Если выключение осознанное — игнорировать;
если нет, вернуть TLS 1.2.

  `composer.json`, `package.json`, `backup.zip`, `db.sql`, `dump.sql`, `.DS_Store`,

  нет, preflight возвращает 403. Кража сессии через межсайтовые запросы закрыта.
- ✅ **TLS сильный:** только TLS 1.3, адекватный шифр, wildcard Let's Encrypt.
- ✅ **Версия nginx не раскрывается** (`server: nginx` без номера).
- ✅ **JSON-эндпоинты API** отдают `X-Frame-Options: DENY`, `nosniff`, `no-referrer`,
  `no-store, no-cache` — для API ровно то, что нужно.
- ✅ `robots.txt` корректно закрывает `/errors/` и `/legal/`.

## 5. Чек-лист для проверки с авторизацией (я этого не делал)

Это места, где на такой архитектуре почти всегда что-то находится. Проверять нужно
изнутри, под своими учётными записями — я оставляю их владельцу.

1. **IDOR в личных сообщениях** — `direct-messages/list.php?user_id=…`: подставить
   чужой `user_id` и убедиться, что сервер проверяет участника переписки, а не доверяет параметру.
2. **`profile/get.php?id=`** — не отдаёт ли лишние поля (email, IP, дата рождения,
   `is_staff`) тому, кому не положено.
3. **`/adm/*` эндпоинты** — `applyAdminVisibility()` в JS лишь прячет кнопку; убедиться,
   что **каждый** `adm/*.php` проверяет роль на сервере. `adm/appeals/bulk_check.php`
   принимает массив `items` — проверить авторизацию по каждому элементу.
4. **`X-Game-Token`** — раз он в `Access-Control-Allow-Headers`, проверить, что токен
   привязан к сессии/пользователю, имеет срок и не даёт доступ к чужому прогрессу.
5. **Загрузка файлов** — `validateImage()` в JS проверяет только `file.type` и размер,
   то есть обходится тривиально. Нужна серверная проверка magic-bytes, перекодирование
   картинок, запрет SVG, выдача с `Content-Type` + `Content-Disposition: attachment`
   для всего, что не картинка. Отдельно — `serializeFiles()` шлёт файлы форума
   в base64 внутри JSON: проверить лимиты и то, что имя файла не попадает в путь.
6. **`auth/validate_username.php`** — позволяет перебирать занятые ники; включить rate-limit.
7. **`users/search.php` и `roblox/users.php`** — второй проксирует Roblox API. Если нет
   кэша и лимитов, сайт превращается в бесплатный прокси к Roblox для посторонних.
8. **`promo/redeem.php`** — rate-limit на пользователя и IP (защита от перебора кодов).
9. **`auth/forgot.php` / `auth/reset.php`** — токен одноразовый, с TTL, сравнение
   постоянное по времени; ответ не должен раскрывать, существует ли email.
10. **`/errors/403` как маршрут** — убедиться, что он не отражает входные данные
    (иначе reflected XSS в обход SPA).

## 7. Приложение: как воспроизводилось

Сбор выполнялся из GitHub Actions (у песочницы собственный TLS-SNI allowlist, под который
`kem-rp.com` не попадает) — запросы при этом самые обычные, от имени анонимного посетителя.
Сырые заголовки и ответы лежат в `relay-out/kem/`, `relay-out/kem2/`, `relay-out/kem3/`.

DNS-часть проверялась прямыми UDP-запросами к `8.8.8.8` (`A`, `AAAA`, `NS`, `MX`, `TXT`,
`SOA`, `CAA`, `_dmarc`, DKIM-селекторы) — без внешних сканеров.
